# 未完成设备探测记录 — 2026-11-09

本文件记录个人 fork 对两台设备的**只读探测结果**。两者**目前都不读电量**，代码里没有对应的电量通道。

## HyperX Cloud III S 无线（飓风3 加强版）— 已抓包核实：固件不提供电量查询

> 2026-11-09 晚间追加：装了 Wireshark + USBPcap 后重启，抓到真实 USB 报文，结论见下。

### 抓包结论（决定性证据）

- NGENUITY 的 `srv-communication-hub` 日志只打开一个 HID 集合：
  `HID#VID_03F0&PID_06BE&MI_03&Col05`，而 **Col05 对应 Usage Page `0x01C0`**（64/64），不是上游 hyperx3 用的 `0xFF13`（Col02）。
- `srv-communication-hub` 与主程序日志里**没有任何 battery / 电量条目**；主程序只记录了 `DeviceModel:"CloudIIISWirelessDTS"` 和 `Device has Audio feature`，随后把耳机当作音频端点分配给音频引擎。**NGENUITY 根本不读这台耳机的电量**。
- 25 秒与 90 秒两份抓包（共 76 MB）里，主机→设备的 HID 命令**一条都没有**：没有 interrupt OUT，control 传输也只有 GET_DESCRIPTOR。设备只主动发出过 4 次 64 字节上报。

### 主动上报的帧（endpoint 0x84，report id 0x0c）

```
0c 02 03 01 00 4d 00 00 ...     (byte5 = 0x4d)
0c 02 03 01 00 02 02 00 ...
0c 02 03 01 00 02 02 00 ...
0c 02 03 01 00 06 3a 0e eb ...
```

前缀 `0c 02 03 01 00` 固定，之后字节含义**未验证**。byte5 在 0x4d / 0x02 / 0x06 之间跳变，不能断定是电量，**因此不做实现**。

### 命令扫描（全部失败）

| 通道 | report id | 扫描范围 | 结果 |
| --- | --- | --- | --- |
| 0xFF13（Col02，62B） | 0x06 | 0x00–0xFF 共 256 个 | 零回包 |
| 0x01C0（Col05，64B） | **0x0c** | 0x00–0xFF 共 256 个 | 零回包 |

注：`0x01C0` 的合法 report id 是 **0x0c**（写 `0c` 打头才不报 `err=87`，写全 0 一律 INVALID_PARAMETER）——这一点已验证，但即使 ID 正确，设备也不回应任何命令。

### 修正：NGENUITY 界面确实显示电量

2026-11-09 22:00 复核（用户指出并截图确认）：NGENUITY 3.0.2 左上角**明确显示电池图标与 58%**。因此「固件不提供电量」这个结论**是错的**，作废。

现有的确定事实：

- 抓到的 4 帧主动上报里有一帧 `0c 02 03 01 00 | 06 | 3a | 0e eb`，其中 **`0x3a` = 58**，与界面数值吻合。
- 但本项目程序**被动监听 0x01C0 拿到 0 帧**（60 秒、180 秒两次，NGENUITY 开/关都试过）——设备不会对普通 HID 打开者主动推帧。
- 76 MB 抓包里**没有主机→设备的 HID 类请求**（control 只有 GET_DESCRIPTOR / SET CONFIGURATION，interrupt 只有 IN 方向），所以「NGENUITY 用什么命令问出电量」仍未定位。要么 USBPcap 在 hub 级别漏抓，要么 NGENUITY 用的是非 HID 路径（系统缓存等）。

### 待办（下一轮）

1. 用 `USBPcapCMD --devices <addr>` 指向单一设备地址重抓，排除 hub 级漏抓。
2. 抓包窗口对准「NGENUITY 启动后第一次读设备」的十几秒，并同时录屏核对界面数值。
3. 若仍无命令，改用 Wireshark GUI + Npcap 复核，或读 NGENUITY 的 `NGENUITY.dll`（.NET）反编译找 HID 调用。

在此之前，HyperX Cloud III S 保持「已识别、电量未实现」，不写入任何猜测解析。

## HyperX Cloud III S 无线（飓风3 加强版）— 早期盲探记录

- USB：`03F0:06BE`，厂商标识 `HP, Inc`，产品名 `HyperX Cloud III S Wireless`
- 现有上游实现 `hyperx3` 只认 `0x05B7 / 0x0C9D`（Cloud III Wireless）与 `0x0995 / 0x0795`（Cloud II Core），不含 `0x06BE`

### 接口清单（实测）

| Usage Page | Usage | Input | Output | Feature |
| --- | --- | --- | --- | --- |
| 0x01C0 | 1 | 64 | 64 | 0 |
| 0x170F | 0x0202 | 8 | 8 | 0 |
| 0xFF13 | 1 | 62 | 62 | 0 |
| 0xFFC0 | 0x0202 | 32 | 32 | 0 |
| 0x000C | 1 | 2 | 0 | 0 |
| 0x000B | 5 | 2 | 2 | 0 |

`0xFF13` 的 value caps 报告：**input report ID = 0x07，output report ID = 0x06**。上游 `hyperx3` 写死的 `0x66 0x89` 前缀在四代上不匹配任何 output report，Windows 直接返回 `err=87`（ERROR_INVALID_PARAMETER）。

### 已尝试

- 用 `0x06` 作 report ID 写 62 字节 → 写入成功，**无任何回包**
- 扫描 `0x06` + 命令字节 0x80–0x8F、0x0D/0x0E/0x0F/0x20 → 全部无回包
- 被动监听 `0xFF13` 6 秒 → 0 帧（设备不会主动上报）
- `0x01C0` / `0x170F` / `0xFFC0` / `0x000B` 全 0 报文写入 → 全部 `err=87`

### 结论与下一步

四代换了协议，靠协议家族推断只能做到「接口认得出来」。要真正读电量，需要抓官方 NGENUITY 的 HID 报文（本机未安装 NGENUITY），或继续有节制地扫命令空间。

## 猛玛 LARK A2（HOLLYLAND）— 已解决，见[LARK A2 适配说明](适配说明-LARKA2.md)

> 2026-11-09 更新：官方 WebHID 网页里的协议已找到，电量读取已实现并实机验证（98%）。下面保留当天的盲探记录作为历史依据。

- USB：`3547:0411`，厂商 `Shenzhen Hollyland Technology Co.,Ltd`，产品名 `Wireless Microphone`
- 复合设备：`MI_00`（HID）、`MI_01`（USB Audio）、`MI_07`（iAP，Windows 显示 Error，属 Apple 协议接口，正常）

### 接口清单（实测）

| Usage Page | Usage | Input | Output | Report ID |
| --- | --- | --- | --- | --- |
| 0xFF90 | 1 | 64 | 64 | 0x55（in/out 同号） |
| 0xFF82 | 1 | 64 | 64 | 0x41（in/out 同号） |
| 0x000C | 1 | 3 | 0 | — |
| 0x000B | 1 | 3 | 3 | — |
| 0x0001 | 6 | 9 | 0 | — |

### 已尝试

- 两个厂商通道被动监听 2.5 秒 → 0 帧
- `0xFF90` 发 `0x55` + 全 0（64 字节）→ 写入成功，无回包
- `0xFF90` 发 `0x55` 后接 `0x0C` / `0x01` / `0x00` → 写入报 `err=1167`（ERROR_DEVICE_NOT_CONNECTED），**该通道随即重新枚举**，旧设备路径失效

### 结论与下一步

这只麦克风接收器在 `0x55` 通道上有「命令会触发重新枚举」的行为，盲试有风险（本次已触发一次掉线，设备随后自愈）。不建议继续盲扫；要么抓猛玛官方 APP 的报文，要么明确标为不支持。

## 与主程序的边界

- 以上两台在界面里会显示为已识别设备，但电量读不出来；主程序按既有规则报「未知」，不会伪造百分比。
- 要落地成功能，需要真实有效回包，而不是模拟测试通过。
